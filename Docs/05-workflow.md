# Как устроена работа

## Роли

- **Автор** (OtherStickmanGames) — геймдизайн, тестирование в Unity, коммит сцен, префабов и
  ассетов, которые меняет редактор (`.meta`, `HUD.prefab`, ассеты рендерера URP и т. д.).
- **ИИ (Claude Code)** — код, шейдеры, editor-скрипты, документация.

## Сессии ИИ

Сессия бывает двух видов — сначала понять, в какой ты:

- **Облачная:** репозиторий клонирован в чистый Linux-контейнер. Всё нужное сохранять коммитом
  и пушем. Перед работой — `git pull origin <ветка>`: автор тоже пушит (сцены, префабы, мета-файлы).
- **Локальная** (десктопное приложение Claude на компьютере автора, Windows, проект в
  `G:\GAME DEVELOPMENT\Project Noob Mini Generals\Noob Mini Generals`): рабочая копия общая с
  автором, его несохранённые в git правки видны сразу — перед изменениями смотреть `git status`
  и не трогать чужие файлы. Shell — PowerShell или Git Bash; `python` там может быть заглушкой
  Microsoft Store (не запускается) — для правок файлов использовать инструменты редактора.

Общее для обеих:

- Рабочая ветка: `claude/gallant-bohr-4bgop6` (коммит и пуш только туда, PR — только по просьбе).
- Между сообщениями ИИ ничего не делает: задача заканчивается вместе с ответом.
- **Скомпилировать и запустить проект ИИ, как правило, не может.** В облаке Unity нет вообще.
  Локально стоит Unity CLI, но в Hub только редактор 6000.x, а проект на **2022.3.62f3** —
  открывать проект другой версией нельзя (он будет сконвертирован). Если нужная версия
  появится — проверять компиляцию через неё. Пока её нет:
  - синтаксис C# проверяется `tree-sitter` (`pip install tree-sitter tree-sitter-c-sharp`);
  - API Unity/URP сверяется с исходниками нужной версии:
    `https://raw.githubusercontent.com/Unity-Technologies/Graphics/2022.3/staging/Packages/...`
    (например, `com.unity.render-pipelines.universal/Runtime/ScriptableRenderer.cs`);
  - HLSL: помнить о зарезервированных словах (`line`, `point`, `triangle` — нельзя как имена переменных);
  - в ответе честно писать «в Unity не проверено»;
  - автор проверяет и присылает ошибки компиляции или скриншоты.
- Логику генерации удобно сначала прототипировать на Python (numpy, opensimplex, PIL) и смотреть
  картинки карт, потом переносить в C#.

## Цикл задачи

1. Понять задачу; для UX — вспомнить, как это сделано в хороших играх (правило в `CLAUDE.md`).
2. Если решение за автором (геймдизайн, спорный выбор) — кратко предложить вариант с рекомендацией и спросить.
3. Сделать, проверить синтаксис, перечитать diff.
4. Обновить README рядом с кодом и документацию в `Docs/`.
5. Коммит (сообщение по-английски, кратко по сути), пуш.
6. Ответ автору: что сделано, что ему сделать в Unity (пересобрать префаб, закоммитить ассеты и т. п.),
   что не проверено.

## Что автору делать после изменений (типовое)

- Изменились поля интерфейса → **Tools → Voxel Arena → Rebuild HUD Prefab** (ручные правки
  префаба пропадут) и коммит префаба. Новые сериализуемые поля с значениями по умолчанию
  пересборки не требуют.
- Изменились значения по умолчанию генерации → поднимается `ArenaGenSettings.CurrentVersion`,
  сцена сама сбросит настройки.
- Настройки вида подобраны в Play mode → Copy Component / Paste Component Values или применить в
  префаб, запушить; ИИ переносит значения в значения по умолчанию в коде.

## Общение с автором

- Язык — русский. Отвечать прямо и по сути, без воды; на вопрос — ответ на вопрос.
- Автор эмоционален, особенно когда видит халтуру или изобретение велосипеда; реагировать делом:
  признать конкретную ошибку одной фразой и исправить, без оправданий.
- Не делать то, о чём не просили: если автор формулирует правило, а не задачу, — не бросаться
  чинить всё подряд (пример: «не надо упрощать UX» было правилом, а не просьбой переделать пункты).
- Автор тестирует на старом ноутбуке; если там нормально — на телефоне тоже, на оптимизацию
  раньше времени не отвлекаться.
